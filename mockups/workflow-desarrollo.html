El pipeline · construir una feature de punta a punta
1
DEFINIR

¿Qué problema resuelve?

conversación · Contexto.md

Antes de tocar código: definir el resultado esperado y confirmarlo. Frenar scope creep — si no acerca el MVP, no va ahora.

✋ Confirmar el qué antes del cómo. No inventar datos: lo que no esté en Contexto.md o Datos_Entrada, se pregunta.
2
DATOS

¿Necesita guardar algo nuevo?

supabase/migrations/

Si la feature guarda datos que aún no existen, se crea una migración numerada y su regla de permisos (RLS).

SÍ → crear 0NN_descripcion.sql + RLS · correr en Supabase
NO → saltar al paso 3
3
TIPOS

Definir el contrato del dato

src/types/

Crear o actualizar el tipo TypeScript (qué campos tiene el dato). Esto guía todo lo demás y evita errores.

4
SERVICE

El puente a los datos

src/services/repositories.ts

Función que lee/escribe en Supabase. Ningún componente accede a la BD directo — todo pasa por aquí.

5
ESTADO + UI

Memoria y pantalla

src/store/ · src/components/

Acción + estado en el store (Zustand); luego el componente/módulo que lee del store y se dibuja. La UI se actualiza sola.

6
PROBAR

Verificar antes de guardar

local

Correr local y revisar que no haya errores de tipos. Revisar seguridad si se tocó auth o pagos.

npm run devnpm run typecheck
7
PUBLICAR

Commit y deploy

git · Vercel

Commit atómico con mensaje descriptivo → push a main. Vercel compila y publica solo. 🚀

git commit -m "feat(x): …"git push origin main
📌 Decisión importante → registrarla en Historial_Decisiones_Project360.md. Al cerrar sesión → /guardar.
Reglas que protegen el proyecto & ciclo largo

🛡️ Guardrails (siempre)

🚫
No inventar datos. Lo que falte, se pregunta.
🔢
Migraciones en orden. Nunca cambiar la BD a mano en prod.
🔌
Un service por cosa externa. Componentes no tocan la BD directo.
⚛️
Commits atómicos + typecheck antes de merge.
🔐
Revisar seguridad en auth / pagos / RLS.
📦
No editar dist/ — es el build.

🔄 El ciclo grande (semanal)

/semana— review ejecutivo: estado, prioridades, decisiones
/build— construir una feature con garantías de calidad
/cliente— briefing antes de una reunión de cliente
/code-review— revisar el diff antes de publicar
/guardar— cerrar sesión documentando avances

Fase actual: terminar el MVP y usarlo con el equipo en clientes reales. Estabilizar antes de sumar features. SaaS (pagos, multi-cuenta) va después.
